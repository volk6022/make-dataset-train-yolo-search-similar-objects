## Проблема и решение

### Контекст и проблема

При разработке систем компьютерного зрения специалист по данным регулярно сталкивается с задачей: найти в большом датасете изображений все пары объектов, которые являются одним и тем же физическим предметом (одна деталь, один товар, один образец), но сфотографированы в разных ракурсах, условиях освещения или на разных кадрах. Без автоматизации это ручная работа: эксперт просматривает тысячи пар изображений и принимает решение «похожи / не похожи» по каждой.

Сложность усугубляется дисбалансом: в реальных датасетах ~95% всех возможных пар — это **разные** объекты, и только ~5% — одинаковые. Стандартные решения (хэширование, простой ResNet) не учитывают ориентацию объектов и дают высокий процент ложных срабатываний.

Дополнительная проблема: при смене предметной области (например, переход от промышленных деталей к геологическим кернам) неясно, какая именно модель эмбеддингов и метод верификации дадут лучший результат. Ручной подбор занимает недели экспериментов.

### Решение

Конвейер из 5 этапов автоматизирует весь процесс с поддержкой 7 embedding-моделей и 9 методов верификации:

1. **Обнаружение объектов** — кастомная YOLOv8-модель с ориентированными bounding box'ами (OBB) находит объекты на каждом изображении с учётом произвольного поворота
2. **Извлечение признаков** — одна из 7 моделей (SigLIP, DINOv2-large/giant, CLIP, RADIO, ViT) преобразует вырезанный объект в вектор 768–1536 измерений
3. **Поиск кандидатов** — L2-нормализованные векторы попарно сравниваются по евклидовой, косинусной или манхэттенской метрике; защита от взрыва: ≤5000 кандидатов передаётся на следующий этап
4. **Многоуровневая верификация** — каждая пара-кандидат независимо проверяется нейросетевыми (XFeat, LightGlue) или классическими (SIFT, ORB) сопоставителями ключевых точек, а также анализом рёбер/углов/блобов/текстуры
5. **E2E-тестирование** — `e2e_test_all.py` систематически прогоняет все 162 комбинации (6 моделей × 3 метрики × 9 верификаторов) с кешированием промежуточных результатов и логированием времени каждого шага

### Измеримый результат

- **7 embedding-моделей** исследованы и сравнены: SigLIP выбран дефолтным (384px вход лучше захватывает слоистую текстуру; sigmoid-loss даёт хорошо разделённые оценки)
- **162 комбинации** конфигураций доступны для автоматического перебора в E2E-тесте
- Порог детектора YOLO: conf ≥ 0.4; тип OBB обрабатывает повёрнутые объекты без потери геометрии
- XFeat: минимум 20 совпадений ключевых точек + дисперсионная проверка (≥70% ячеек сетки 10×2)
- LightGlue: порог confidence ≥ 0.5 на совпадение; поддержка SuperPoint, DISK, ALIKED экстракторов
- Защита производительности: максимум 5000 пар-кандидатов передаётся на верификацию
- Подтверждённый датасет ~500 верифицированных пар (два независимых метода)
- [NEEDS VERIFICATION] — сравнение точности между моделями на валидационном наборе
- [NEEDS VERIFICATION] — время обработки одного датасета vs. ручная разметка

## Архитектура

### Компоненты системы

```
[Входные изображения CVAT-датасета]
          ↓
[image_processing.py]
  Resize до 640×640, LANCZOS
          ↓
[yolo_process.py]
  YOLOv8 OBB, conf=0.4
  → OBB-координаты (8 чисел на объект)
          ↓
[get_yolo_pred_and_embeddings.py]  ← координирует
  crop_obb_from_image()           ← warpPerspective
  get_embedding()                 ← SigLIP / DINO / CLIP / RADIO / ViT
          ↓
[predictions_with_embeddings.json]
          ↓
[searching_similar.py]
  L2-нормализация → itertools.combinations
  Косинус / Евклид / Манхэттен + cap 5000 пар
          ↓
[similarity.json] — кандидаты
          ↓
[similarity_verification.py]
  ├─→ XFeat (нейронные ключ. точки) ← ДЕФОЛТ
  ├─→ LightGlue (SuperPoint/DISK/ALIKED) ← НОВЫЙ
  ├─→ SIFT + FLANN + Lowe's ratio + дисперсия
  ├─→ ORB + BFMatcher
  ├─→ Canny edge + NCC
  ├─→ Corner / Blob / Texture + SSIM
  └─→ Hu moments (логарифмические, L1)
  Все: дисперсионная проверка (сетка 10×2, ≥70%)
  Любой метод может подтвердить пару → OR-логика
          ↓
[similarity_verified.json] — финал
          ↓
[image_processing.create_image_collages()]
  Коллажи для ручного аудита
```

### Ключевые алгоритмы и паттерны

**Перспективное вырезание объектов (OBB crop):**
Не прямоугольный crop, а `cv2.getPerspectiveTransform` + `warpPerspective` с переориентацией точек (высота > ширина). Сохраняет геометрию повёрнутых объектов.

**XFeat — нейронные ключевые точки:**
Загружается через `torch.hub` без pip install, работает на CPU. Ускоренное нейронное сопоставление — превосходит SIFT на повторяющихся текстурах (типичная проблема геологических/промышленных объектов).

**LightGlue — transformer-сопоставитель:**
Комбинирует детектор (SuperPoint/DISK/ALIKED) с трансформером для сопоставления. Фильтрация по confidence ≥ 0.5. Кеширование модели глобально (`_lightglue_cache`) — избегает переинициализации при обработке тысяч пар.

**Дисперсионная проверка совпадений:**
Сетка 10×2, порог ≥70% занятых ячеек — предотвращает кластерные ложные совпадения, когда все точки сосредоточены в одном углу изображения. Реализована с `@jit` компиляцией через Numba.

**Защита от взрывного роста:**
`max_candidate_pairs_to_verify = 5000` — cap перед верификацией, сортировка по убыванию сходства. Предотвращает неконтролируемое время выполнения при слабых порогах.

### Поток данных

```
Изображения CVAT → 640×640
→ YOLO OBB → OBB-координаты
→ warpPerspective → кроп 224×224 / 384×384
→ SigLIP/DINO/CLIP/RADIO → float[768–1536]
→ L2-нормализация → cosine/euclidean/manhattan
→ отфильтрованные кандидаты (≤5000)
→ XFeat/LightGlue/SIFT (≥20 совпадений, дисперсия≥70%)

```

## Бизнес-ценность и целевые клиенты

### Кому это нужно

**Основная аудитория:**
- **ML-инженеры и data scientists** в компаниях, которые собирают собственные датасеты для компьютерного зрения (производство, геология, ритейл, медицина)
- **Исследовательские лаборатории** с доменно-специфичными датасетами: нужно быстро понять, какая модель эмбеддинга лучше работает на их объектах
- **Аутсорсинговые компании по разметке данных** — ускоряют этап проверки дублей в больших датасетах
- **Геологические и производственные структуры** — исходный кейс: поиск идентичных образцов почвы (керн) на разных фото

### Боль, которую закрывает

Без этого инструмента data scientist вручную открывает пары изображений и решает «это один объект или разные?» — для датасета из 500 изображений с 10 объектами каждое число потенциальных пар исчисляется миллионами. Инструмент отфильтровывает нерелевантные пары и выдаёт только верифицированные совпадения с коллажами для финального аудита.

Дополнительная боль: подбор оптимальной модели под новый домен стоил раньше недель работы. E2E-тест из 162 комбинаций даёт этот ответ автоматически за один запуск.

### Альтернативы на рынке

| Вариант | Ограничение |
|---------|------------|
| Ручной просмотр | Не масштабируется: линейный рост трудозатрат |
| Простое хеширование | Не справляется с разными ракурсами/освещением |
| FAISS + ResNet | Нет OBB, нет верификации, нет сравнения моделей |
| Дорогие SaaS | Стоимость при больших объёмах, нет кастомизации детектора |
| Ручной подбор модели | Недели экспериментов vs. автоматический E2E-прогон |

### Потенциальный ROI

Для компании с командой из 3 разметчиков, собирающей датасет 1000 изображений:
- Ручная верификация дублей + подбор модели: ~80 ч/проект
- При автоматизации: ~3–4 ч (запуск E2E + финальный аудит коллажей)
- [NEEDS VERIFICATION] — точные данные зависят от конкретного датасета и доли дублей

### Смежные применения

- **Дедупликация датасетов** перед обучением — предотвращает train/test leakage
- **Поиск дублей в товарных каталогах** (e-commerce) — одна SKU, несколько фото
- **Идентификация ранее встреченных дефектов** в новых производственных партиях
- **Создание hard negatives** для contrastive learning — «почти похожие» пары

### Bullet points для резюме

- Провёл сравнительное исследование 7 vision-моделей (SigLIP, DINOv2-large/giant, CLIP, RADIO, ViT, SD-VAE) для задачи поиска сходства, выбрав SigLIP как оптимальную для доменно-специфичных текстурных объектов
- Перевёл проект на воспроизводимую среду через `pyproject.toml + uv.lock` (Python ≥3.11), включая git-зависимости (LightGlue) через uv git source
- Оптимизировал вырезание объектов через `cv2.getPerspectiveTransform` (OBB warp) и защитил масштабируемость через cap на 5000 кандидатов перед верификацией

**make-dataset-train-yolo-search-similar-objects** — автоматизированный пайплайн поиска идентичных объектов в датасетах изображений с систематическим сравнением 162 конфигураций (7 embedding-моделей × 3 метрики × 9 верификаторов). ### Кейс для портфолио

ПРОБЛЕМА: Исследователи, создающие датасеты для компьютерного зрения, тратят десятки часов на ручной поиск дублирующихся объектов и ещё больше — на подбор оптимальной модели эмбеддинга под свой домен. При 500 изображениях число потенциальных пар исчисляется миллионами, а выбор между DINOv2, CLIP и SigLIP без инфраструктуры сравнения занимает недели.

РЕШЕНИЕ: Разработан пятиэтапный пайплайн: YOLO OBB детектирует объекты с учётом поворота → 7 embedding-моделей извлекают признаки 768–1536 измерений → нормализованное расстояние отбирает ≤5000 кандидатов → XFeat/LightGlue/SIFT верифицируют геометрически. E2E-тест из 162 конфигураций с resume-кешированием позволяет найти лучшую связку за один автоматический прогон.

РЕЗУЛЬТАТ: SigLIP выбран оптимальной моделью для доменно-специфичных текстурных объектов. Система сводит миллионы потенциальных пар к компактному списку с коллажами для финального аудита. Полная воспроизводимость через pyproject.toml + uv.lock.

- **DevOps-практики:** pyproject.toml + uv.lock — воспроизводимость вместо случайных версий

## Ограничения и зоны роста

- **E2E без unit-тестов** — тестируется поведение системы целиком, но отдельные функции не покрыты
- **O(n²) сравнение пар** — при тысячах объектов cap на 5000 пар помогает, но FAISS дал бы логарифмическое ускорение
- **Зависимость от GPU** — SigLIP и DINOv2-giant требуют CUDA для приемлемой скорости; только XFeat спроектирован CPU-friendly
- **Нет Docker/контейнеризации** — uv-среда упрощает воспроизводимость, но нет изоляции для GPU-зависимостей
- **Сиамская сеть — эксперимент, не production-ready** — переобучение из-за малого датасета (~500 пар) и дисбаланса 95/5
- **Нет мониторинга** — Tensorboard/W&B не интегрированы; только файловые логи и print
- **Конфиг-пути частично захардкожены** в `Settings` — затрудняет быстрое переключение на новый датасет без правки кода

### Что можно улучшить для production

1. **FAISS/ScaNN** — приближённый nearest-neighbor поиск вместо O(n²), масштабирует на миллионы объектов
2. **REST API (FastAPI)** — обернуть пайплайн в сервис с эндпоинтом `/find-similar`
3. **Unit-тесты (pytest)** — покрыть `searching_similar.py` и `image_processing.py`
4. **Docker Compose с GPU** — воспроизводимая среда поверх uv
5. **CLI через Typer** — запуск каждого этапа из командной строки с параметрами, без правки кода
